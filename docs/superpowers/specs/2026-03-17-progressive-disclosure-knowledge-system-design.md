# Progressive Disclosure Knowledge System

**Date:** 2026-03-17
**Scope:** Global (all projects under Science portfolio and beyond)
**Status:** Approved — ready for implementation

---

## Problem Statement

The current knowledge infrastructure loads 1,000–4,300 lines of `.living/` files at every session start, with no mechanism for cross-project knowledge transfer beyond manual entries in `Science/.living/learnings.md`. Knowledge is siloed per-project, stale entries persist indefinitely, and there is no formal governance over the growing corpus.

Progressive disclosure solves this by layering information: compact indexes always in context, domain-specific knowledge loaded on demand, and project-local detail accessed only when the task requires it.

## Design Principles

1. **Index-first, pull-on-demand** — the agent always sees lightweight pointers; it reads full content only when the task matches
2. **Agent-as-router** — the LLM's natural reasoning matches tasks to relevant knowledge via `when_useful` trigger conditions
3. **Silent self-maintenance** — the system audits itself weekly without user intervention unless high-impact issues arise
4. **Transferable knowledge flows up** — project-local learnings that apply broadly get promoted to global domain files
5. **Mycelium-intrinsic** — audit, promotion, and governance are part of the mycelium skill, ensuring a closed self-maintaining system

## Architecture: Three-Tier Read Path

### Tier 1 — Always in Context (~20 lines per project)

Each project's `MEMORY.md` (auto-loaded by Claude Code) includes a standardized global knowledge section:

```markdown
## Global Knowledge Domains
| Domain | Summary | File |
|--------|---------|------|
| skills | Mycelium + available skills with trigger conditions | ~/.claude/knowledge/skills.md |
| external-apis | Rate limits, auth, backoff, publisher access | ~/.claude/knowledge/external-apis.md |
| data-pipelines | DAG design, snapshots, retry, orchestration | ~/.claude/knowledge/data-pipelines.md |
| ... | ... | ... |

Check domains relevant to your current task before starting work.
```

Additionally, the CLAUDE.md session-start instruction changes from "silently read all `.living/` files" to "read `.living/INDEX.md`" — a compact auto-generated summary.

**`.living/INDEX.md` format (auto-generated by weekly audit):**

```markdown
# .living/ Index
Last audit: 2026-03-17

| File | Entries | Last updated | Key topics |
|------|---------|-------------|------------|
| conventions.md | 45 sections | 2026-03-15 | async patterns, structlog, Pydantic models |
| decisions.md | 12 entries | 2026-03-14 | shared-corpus optimization, depth profiles |
| learnings.md | 8 entries | 2026-03-16 | Elsevier access, rate limiting, DAG snapshots |
```

### Tier 2 — Domain Files (read on demand, ~50-100 lines each)

Location: `~/.claude/knowledge/{domain}.md`

Each file contains accumulated entries for that domain. Entries include `when_useful` trigger conditions so the agent can scan for relevance quickly.

### Tier 3 — Project-Local Detail (existing `.living/`, read on demand)

Full `.living/` files (conventions.md, decisions.md, learnings.md) are read only when the task warrants it. The INDEX.md provides enough context for the agent to decide whether to drill down.

## Architecture: Structured Write Path

### Entry Template

All entries across all tiers use a consistent format:

```markdown
### [domain-tag] One-line summary
**What:** The concrete fact or pattern (2-3 sentences max)
**Evidence:** Project, date, what happened
**When useful:** Trigger condition — what task/situation makes this relevant
**Scope:** project-local | transferable
**Status:** active | unreviewed | archived
**Last validated:** YYYY-MM-DD
```

### Promotion Flow

```
Agent learns something during a session
        |
    "Is this project-specific?"
     yes -> append to .living/learnings.md
     no  |
        v
    "Which global domain does this fit?"
     existing domain -> append to ~/.claude/knowledge/{domain}.md (status: unreviewed)
     no fit -> append to project .living/, flag for audit to evaluate new domain creation
        |
        v
    Weekly audit reviews unreviewed entries silently
```

### Decision Criteria for Promotion

The agent applies this test: "Would a different project, in a different domain, encounter this same issue?" If yes, promote. If unsure, keep project-local — the weekly audit can promote later if the pattern recurs.

### Domain Governance Rules

- Index stays at domain level — one line per domain, never individual entries
- Domain file >100 lines → split into sub-topics (e.g., `external-apis/publishers.md` + `external-apis/rate-limiting.md`)
- New domain creation requires 3+ entries that don't fit existing domains
- Weekly audit validates these thresholds

## Weekly Silent Audit

### Trigger

SessionStart hook checks `~/.claude/knowledge/.last-audit` timestamp. If >7 days old, emits a silent directive for the agent to dispatch a haiku subagent that performs the audit in the background.

### Audit Steps

1. **Staleness scan** — entries where `last-validated` >60 days get flagged
2. **Caveat resolution** — entries with 2+ caveats get proposed rewrites or archival
3. **Unreviewed promotion** — entries tagged `unreviewed` get evaluated: confirm → `active`, reject → `archived`
4. **INDEX.md regeneration** — each project's `.living/INDEX.md` rebuilt with current entry counts, topics, last-updated dates
5. **Domain health** — domain files >100 lines flagged for splitting
6. **Skills sync** — verify `skills.md` routing table matches installed skills
7. **Cross-project dedup** — identify near-duplicate entries across project `.living/` files and global domains

### Output Severity

| Severity | Action |
|----------|--------|
| Routine (stale confirmed, indexes rebuilt, unreviewed promoted) | Silent — write results, no user notification |
| Notable (entries archived, domains split, contradictions resolved) | Single-line summary appended to session context |
| High-impact (knowledge contradicts active work, missing critical domain, major staleness) | Surface to user for decision |

### Audit Artifacts

- `~/.claude/knowledge/.last-audit` — timestamp + one-line summary
- `~/.claude/knowledge/.audit-log.md` — append-only log, agent can reference if asked

## Feedback Loop: Caveat System

### How Caveats Work

When an agent retrieves a knowledge entry and finds it contradicts observed behavior:

1. Agent appends `**Caveat [YYYY-MM-DD]:** [what was different and why` to the entry
2. Agent proceeds with the correct behavior (does not block on the contradiction)
3. Contradictions are handled silently unless they have potential to directly impact the user's session

### Caveat Resolution (via weekly audit)

- 1 caveat: entry stays active, caveat noted in audit log
- 2+ caveats: audit proposes rewrite or archival, resolves silently
- Caveat contradicts a safety/correctness pattern: surfaced to user

## Changes to Existing Infrastructure

### CLAUDE.md Session-Start Instructions

**Before:**
```
At the start of every session, silently read the following files:
1. .living/conventions.md, .living/decisions.md, .living/learnings.md
2. Science/.living/learnings.md
3. .living/skills/ACTIVE_SKILLS.yaml
```

**After:**
```
At the start of every session:
1. Read .living/INDEX.md (compact summary of project knowledge)
2. Check MEMORY.md global knowledge domains for task-relevant context
3. Read full .living/ files only when the current task touches those areas
```

### MEMORY.md Per-Project Updates

Each project's MEMORY.md gets the standardized global knowledge domain table appended. This is the always-in-context routing layer.

### Mycelium Skill Integration

The weekly audit becomes intrinsic to the mycelium skill:
- Audit trigger logic added to SessionStart hook (check `.last-audit` age)
- Audit execution via haiku subagent (silent, background)
- Audit convention documented in mycelium skill definition
- Knowledge promotion documented as part of the `.living/` update convention

## Success Criteria

1. Session-start context load drops from 1,000-4,300 lines to <100 lines (INDEX.md + MEMORY.md domain table)
2. Cross-project knowledge is discoverable from any project via the global domain index
3. Knowledge entries include `when_useful` triggers that enable accurate agent routing
4. Weekly audit runs silently without user intervention in >90% of cases
5. Stale entries are caught within 60 days, contradictions within 2 audit cycles
6. The skills domain keeps the mycelium system self-referential and closed
